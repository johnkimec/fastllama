Qwen3.8-27B, 4-bit, M1 Max, the same file Ollama loads

Wider loads, 14.24 tokens a second.

Decode on this chip is a read of the weights. The mat-vec kernel was loading those bytes a few at a time. Reading the activation as a float4 and each Q4_K weight slice as a uint2 raised mean decode from 13.17 to 14.24 tokens per second. Prefill stayed flat. Memory did not drop.

  • 14.24 tok/s mean decode, ten warm runs
  • +8.12% versus Ollama’s 13.17
  • 59% of the ceiling 24.17 tok/s at 400 GB/s

One read of the weights is 24.17 tok/s.

The file is about 16.6 GB of weights. At 400 GB/s, one full read per generated token is 24.17 tok/s. Ollama uses 54.5% of that. This build uses 58.9%. The 10% line was 14.49 tok/s.

The kernel already had the bytes. It was fetching them narrowly.

Q4_K is 73% of the file, 12.08 GB. In kernel_mul_mv_q4_K_f32 the activation had been one float at a time and the weight slice one uint16 at a time. The kept edit loads sixteen bytes of activation and eight bytes of weights, then unpacks into the same scalar multiply as before.

float4 a0 = ((device const float4 *)(y4 + 0))[0];
uint2 q1v = ((device const uint2 *)q1)[0];

That change, alone, measured 14.18 tok/s. Q6_K is the other 27%. Its activations are also loaded as float4 in the settled kernel. Those loads added about 0.06 tok/s, and the two spreads meet. The Q6 weight bytes stay one byte at a time: a block is 210 bytes, so a wider integer load is misaligned on odd blocks. The patch is both edits, against llama.cpp 0f3a71be1.

patches/mul_mv-wide-loads.patch

Prefill and memory stayed where they were.

The pass rule wanted 10% on prefill, decode, and steady-state footprint together. Decode is short of that. The other two did not move. Two later edits of the same kernel measured slower, so they are not in the patch.
